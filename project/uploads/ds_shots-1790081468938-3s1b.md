# startSmartBuy.md — wytyczne dla programisty LLM

> Ten plik to punkt startowy projektu. Przeczytaj go w całości przed napisaniem pierwszej linii kodu.
> Gdy coś tu jest niejasne lub sprzeczne z rzeczywistością (np. zmieniło się API serwisu), **zatrzymaj się i zapytaj**, zamiast zgadywać.

---

## 1. Cel produktu

**Smart Buy** to rozszerzenie Chrome, które automatycznie śledzi oferty na **OLX.pl**, **Vinted.pl/com** i **Allegro.pl**.

Główny flow użytkownika:
1. Dodaje produkt: nazwa, słowa kluczowe / możliwe opisy, słowa wykluczające, zakres cen, (opcjonalnie) lokalizacja, stan, rozmiar.
2. Wybiera serwisy i częstotliwość sprawdzania.
3. Dostaje powiadomienie **w przeglądarce** i **mailem**, gdy pojawi się nowa pasująca oferta (lub cena spadnie).

Priorytety w kolejności: **niezawodność powiadomień → brak spamu (duplikatów) → prostota UI → reszta.**

---

## 2. Zakres MVP (tylko to, nic więcej)

- [ ] Watchlista: CRUD produktów z polami z sekcji 1
- [ ] Adaptery: OLX, Vinted, Allegro (wspólny interfejs)
- [ ] Harmonogram sprawdzeń per produkt (`chrome.alarms`)
- [ ] Deduplikacja: powiadomienie tylko o ofertach niewidzianych wcześniej
- [ ] Powiadomienia `chrome.notifications` (klik → otwiera ofertę)
- [ ] Mail: natychmiastowy lub digest (wybór użytkownika) przez backend
- [ ] Monitoring parserów: alert, gdy adapter zwraca błąd lub 0 wyników wielokrotnie z rzędu
- [ ] Strona opcji: lista produktów, ostatnie znalezione oferty, status adapterów

Poza MVP (NIE implementuj bez polecenia): historia cen, AI-scoring, Telegram, wyszukiwanie po zdjęciu, synchronizacja między urządzeniami, inne serwisy.

## 3. Stack (decyzje zamknięte)

| Warstwa | Technologia |
|---|---|
| Rozszerzenie | Chrome **Manifest V3**, **TypeScript (strict)** |
| Build | Vite + CRXJS |
| UI (popup, options) | Preact + prosty CSS (bez ciężkich bibliotek UI) |
| Walidacja danych | Zod |
| Storage lokalny | `chrome.storage.local` (konfiguracja), IndexedDB przez `idb` (oferty, seen IDs) |
| Backend | Supabase: Postgres + Edge Functions (maile, OAuth Allegro) |
| Mail | Resend |
| Testy | Vitest + fixtures HTML/JSON |
| Lint/format | ESLint + Prettier |

Zmiana stacku wymaga uzasadnienia i zgody.

## 5. Kluczowe kontrakty

```ts
export type SiteId = 'olx' | 'vinted' | 'allegro';

export interface SearchQuery {
  keywords: string[];          // dowolne z nich
  excludeKeywords: string[];   // żadne z nich
  priceMin?: number;
  priceMax?: number;           // PLN
  location?: { city: string; radiusKm?: number };
  condition?: 'new' | 'used' | 'any';
  extra?: Record<string, string>; // np. rozmiar na Vinted
}

export interface NormalizedOffer {
  site: SiteId;
  externalId: string;          // ID z serwisu — klucz deduplikacji
  url: string;
  title: string;
  price: number | null;        // PLN, null gdy "za darmo"/"do negocjacji"
  currency: 'PLN' | string;
  imageUrl?: string;
  location?: string;
  postedAt?: string;           // ISO
  seller?: { name?: string; rating?: number };
  raw?: unknown;               // tylko w trybie debug
}

export interface SiteAdapter {
  id: SiteId;
  minIntervalMs: number;       // twardy limit częstotliwości dla serwisu
  search(q: SearchQuery, signal: AbortSignal): Promise<NormalizedOffer[]>;
  healthCheck(): Promise<'ok' | 'degraded' | 'broken'>;
}
```

Kluczem deduplikacji jest `${site}:${externalId}`. Zmiana ceny dla znanego klucza = zdarzenie `price_changed`, nie `new_offer`.

## 6. Zasady twarde (MUST / MUST NOT)

**Ogólne**
1. **MUST** pracować małymi krokami: plan → implementacja jednego modułu → testy → commit. Jeden commit = jedna logiczna zmiana.
2. **MUST** przed każdym większym zadaniem wypisać krótki plan i listę plików, które zmienisz.
3. **MUST NOT** wymyślać endpointów, selektorów CSS ani struktur JSON serwisów. Najpierw zapisz prawdziwą odpowiedź do `tests/fixtures/`, potem pisz parser pod nią.
4. **MUST NOT** dodawać zależności bez uzasadnienia w opisie commita.
5. **MUST NOT** wychodzić poza zakres MVP bez wyraźnego polecenia.

**Manifest V3**
6. Service worker jest **ulotny**: **MUST NOT** trzymać stanu w zmiennych globalnych. Wszystko, co ma przetrwać, idzie do storage.
7. Listenery (`chrome.alarms.onAlarm`, `runtime.onMessage` itd.) **MUST** być rejestrowane synchronicznie na najwyższym poziomie skryptu.
8. Brak `DOMParser` i `localStorage` w service workerze — parsowanie HTML tylko w **offscreen document**.
9. `host_permissions` **MUST** ograniczać się do domen trzech serwisów i backendu.

**Scraping i serwisy**
10. **MUST** respektować `minIntervalMs` per serwis (domyślnie: OLX 5 min, Vinted 5 min, Allegro zgodnie z limitami API), niezależnie od ustawień użytkownika.
11. **MUST** dodawać losowy jitter (±20%) do interwałów i wykonywać zapytania sekwencyjnie per serwis, nigdy równolegle w dużej liczbie.
12. **MUST** przy 429 / 403 / captchy: exponential backoff, oznaczenie adaptera jako `degraded`, powiadomienie użytkownika po N kolejnych porażkach. **MUST NOT** próbować obchodzić captchy.
13. Allegro: **MUST** korzystać z oficjalnego REST API. `client_secret` wyłącznie w backendzie. Przed implementacją zweryfikuj w dokumentacji, czy aplikacja ma dostęp do wyszukiwania ofert — jeśli nie, zgłoś to jako blocker.
14. Vinted: zapytania z kontekstu przeglądarki użytkownika (sesja/cookies). Zweryfikuj, czy fetch z service workera przenosi potrzebne cookies; jeśli nie — fallback przez content script w karcie serwisu. Udokumentuj wybór w `docs/`.
15. OLX: preferuj JSON zwracany przez stronę nad parsowaniem HTML; parser HTML jako fallback.

**Bezpieczeństwo i prywatność**
16. **MUST NOT** umieszczać w rozszerzeniu żadnych sekretów (klucze API, Resend, Allegro secret).
17. **MUST** walidować Zodem wszystkie dane przychodzące z serwisów i z backendu.
18. **MUST NOT** wysyłać na backend historii przeglądania ani cookies użytkownika. Backend dostaje tylko to, co potrzebne do wysłania maila (adres, lista ofert).
19. **MUST** escapować treści ofert w UI i w mailach (tytuły z serwisów to niezaufany input).

**Powiadomienia**
20. **MUST** grupować: jeśli w jednym sprawdzeniu jest > 3 nowe oferty dla produktu, wyślij jedno zbiorcze powiadomienie.
21. **MUST NOT** powiadamiać o ofertach sprzed dodania produktu do watchlisty (pierwsze sprawdzenie = cichy "baseline").

## 7. Dobre praktyki

- **Adapter = izolacja.** Awaria jednego serwisu nie może zatrzymać pozostałych (`Promise.allSettled`, osobne try/catch).
- **Matcher niezależny od serwisów.** Filtrowanie słów kluczowych, wykluczeń i ceny robi `core/matcher.ts` na `NormalizedOffer`, nie adaptery. Normalizuj tekst: małe litery, usunięte polskie znaki diakrytyczne do porównań, trim.
- **Testy parserów na fixtures.** Każdy adapter ma testy na minimum 2 prawdziwych odpowiedziach (w tym pusty wynik). Zmiana struktury strony = nowa fixture + poprawka + test.
- **Health check jako test dymny.** Adapter uruchamia okresowo znane zapytanie; 0 wyników lub błąd parsowania 3× z rzędu = status `broken` widoczny w opcjach.
- **Logger z poziomami** (`debug/info/warn/error`), bufor ostatnich ~500 wpisów w storage, podgląd w opcjach. Bez logowania danych osobowych.
- **Czytelne nazwy, małe funkcje**, brak `any`. Komentarze wyjaśniają *dlaczego*, nie *co*.
- **ADR-y** (`docs/adr-XXX.md`) dla decyzji, które nie są oczywiste: np. sposób pobierania Vinted.
- **Migracje storage** wersjonowane (`schemaVersion`), żeby aktualizacja rozszerzenia nie gubiła watchlisty.
- **UI po polsku**, kod i komentarze po angielsku.

## 8. Kolejność pracy

1. Szkielet repo, build MV3, pusty popup i options, CI z lintem i testami.
2. `types.ts`, schematy Zod, warstwa storage z migracjami.
3. Scheduler (`chrome.alarms`) + rate-limiter + jitter.
4. Adapter **Allegro** (najstabilniejszy — oficjalne API) + backend OAuth/search.
5. Matcher + dedup + powiadomienia w przeglądarce → **pierwsze działające E2E**.
6. Adapter **OLX** (fixtures najpierw).
7. Adapter **Vinted** (fixtures + ADR o sposobie pobierania).
8. Backend: `send-email` (Resend), tryb natychmiastowy i digest.
9. Health checki, status adapterów w UI, logi.
10. Szlif UI, testy manualne według checklisty z sekcji 9.

Po każdym kroku: krótkie podsumowanie co zrobione, co nie działa, jakie są pytania.

## 10. Backlog po MVP (tylko do wiadomości)

- **v1:** historia cen, alert spadku ceny, wskaźnik okazji (cena vs mediana), ciche godziny, digest dzienny, podgląd ofert w popupie z akcjami „obserwuj/odrzuć".
- **v2 (AI):** LLM ocenia dopasowanie oferty do opisu produktu, analiza zdjęć (uszkodzenia, stockowe zdjęcia), wykrywanie scamu, generator wiadomości do sprzedającego.
- **Później:** Telegram/Discord/SMS, wyszukiwanie po zdjęciu, łączenie tej samej rzeczy z wielu platform, kalkulator marży resell, współdzielone watchlisty, PWA, eksport CSV, kolejne serwisy (eBay, FB Marketplace, Otomoto, Sprzedajemy).

Architektura MVP powinna to umożliwiać (adaptery, znormalizowany model ofert, historia w IndexedDB), ale **nie implementuj tego teraz**.
